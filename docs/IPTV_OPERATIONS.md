# Authorized provider metadata pulling and scheduling

## IMPLEMENTED BUT UNVERIFIED (full external acceptance)

New `XtreamProviderAdapter` retrieves actual Xtream live/movie/series and three category lists via six bounded HTTPS POSTs using pinned DNS, TLS certificate/hostname verification,2MiB per list/12s attempt deadline. Credentials are decrypted server-side and form-encoded, never in URLs or returned rows. Metadata names redact credential echoes. Full six-list normalization rejects partial/malformed exports; no failed pull replaces the previous catalog. Existing provider CRUD/default/priority/health/encryption remain unchanged.

`POST /admin/xtream-servers/:id/catalog-sync/pull` requires the existing AdminJwtGuard, DB permission xtream:manage, verified tenant and explicit authorizationConfirmed=true. Tenant-scoped enabled provider lookup precedes any connection. Endpoint never accepts a client-selected origin/password. Manual and scheduled paths share one runner. This is metadata synchronization, not playback authorization or a claim of complete episode/artwork synchronization.

Opt-in automatic schedule: server-only `XTREAM_SYNC_SCHEDULE` JSON array of `{tenantId,serverId,intervalSeconds,authorizationConfirmed:true}`. IDs must be UUIDs, intervals300–86400seconds, maximum20unique providers. No schedule means no autonomous network access. Invalid schedule fails startup. Poll60seconds; recent success OR failure suppresses work until interval. Provider errors do not prevent other entries. Do not enable this against an unverified/unauthorized provider or production without approval.

Runner uses PostgreSQL transaction-scoped advisory lock (`sync-pull:<serverId>`) across replicas, plus local duplicate/cap2guard. Network work holds that bounded lock transaction (60s max/2s pool wait); catalog import is a separate short transaction with its existing import lock. Pool must allow concurrent lock/import connections (at least4per active instance, coordinate total DB connection budget). No persistent queue is introduced. Three transient attempts maximum with500/1000ms exponential pauses, no retry on explicit credential rejection. Failed pulls record sanitized reason/time/history while retaining last-success catalog. Shutdown aborts requests/backoff; process crash releases DB lock and a stale schedule retries on a future poll. Interrupted attempts do not yet have durable queued/cancelled-job records or cross-replica user cancellation; do not describe this as a complete job queue.

Existing Admin panel now includes explicit authorized pull confirmation, busy/error/retry-by-action, statistics and last20history records. Existing colors/components preserved. Failed request instructs operator to refresh history before retry (request may have completed after proxy timeout). Admin bridge permits65s only for validated sync-pull paths; deployment runtime duration support remains unverified and may require an approved infrastructure change. No deployment performed.
